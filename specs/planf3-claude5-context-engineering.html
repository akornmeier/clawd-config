Purpose

Rewrite the planf3 skill so it matches how Anthropic now says to write context for Claude 5 generation models: a lean, discoverable SKILL.md; real progressive disclosure instead of one monolithic file; judgment-level guidance instead of prescriptive rules; a rich HTML reference instead of a fenced code block; and evaluations so future changes to the skill can be measured rather than guessed at.

The skill's behaviour does not change. Its four workflows, its HTML-first output, its append-only metadata and its image sub-workflow all survive. What changes is where the bytes live and when they load.

Problem

skills/planf3/SKILL.md is 241 lines, and 175 of them (73%) are an inline HTML plan template that only two of the four workflows ever use. Because it lives inside SKILL.md, it loads on every trigger — including Build Plan and Update References runs that never touch it. That is the exact pattern the Claude 5 guidance calls out: information delivered up front instead of at the moment it is needed.

Solution

Five moves, in dependency order. The template comes out first because everything else in SKILL.md is written around it; the rest is subtraction.

  1. Extract the template to templates/plan.html and give it the <style> block it always assumed. This removes 175 lines from the always-loaded path and upgrades the template from a fenced code block to a real HTML artifact — the format the guidance says produces better results than a description.
  2. Rewrite the description with what it does, when to use it, and its trigger terms, in third person, so the skill fires on all four of its workflows rather than one.
  3. Cut the instructions from eighteen bullets to the handful Claude cannot derive: the output contract, the identity contract, append-only metadata, length calibration, scope discipline.
  4. Fix the workflow files: skill-relative script paths, conditional doc reads, no duplicated thinking instructions.
  5. Add three evaluations so the next edit to this skill can be measured against a baseline.

Notes

What the research actually says

The Claude 5 context-engineering post is a subtraction argument: Anthropic removed over 80% of Claude Code's system prompt for these models with no measurable loss on coding evaluations. Four of its five "then vs now" pairs land directly on this skill.

ThenNowWhat it costs planf3 today
Give Claude rulesLet Claude use judgmentFour instruction bullets that restate general engineering competence.
Give Claude examplesDesign interfacesMostly fine — the workflow routing table is an interface. The template is the exception, and it stays: it is an output contract, not an example.
Put it all upfrontUse progressive disclosure175 lines loaded on every trigger. The headline finding.
Repeat yourselfSay it once, where it's usedThinking instructed three times; image rules stated in two files.

The fifth pair — use rich references — is the one this plan leans into hardest. "HTML mockups of a design will generally produce better results than a description" is precisely the argument for moving the template out of a markdown fence and into a file that renders.

Verification is not over-verification

The Opus 5 prompting guide says to remove explicit verification instructions, because the model already verifies and the instruction compounds into wasted tokens. That applies to prompt scaffolding ("double-check your answer", "use a subagent to verify"). It does not apply to build-plan.md's loop, where a command runs and its exit status is observable — the skill-authoring guidance explicitly endorses validator loops of exactly that shape. This distinction is why Phase 3 changes nothing in build-plan.md, and why that non-change is worth writing down.

Rejected approaches

Rename the skill to gerund form (planning-implementations)

Authoring guidance prefers gerunds, and planf3 is exactly the kind of opaque name it warns about. Rejected anyway: /planf3 is the user's daily entry point, and a rename breaks every existing invocation and reference for a benefit the description field delivers on its own. Discoverability is a description problem here, not a name problem.

Split the template into per-section partials

Considered, since progressive disclosure is the theme. Rejected: Create consumes the template whole, so splitting saves nothing and pushes references two levels deep from SKILL.md — which the guidance specifically warns causes partial reads. One file, one hop.

Delete the gpt-image scripts

They are inert on this machine — OPENAI_API_KEY is unset, so the backend check always routes to diagram-design. Kept anyway: they are the documented alternative backend, they sit at L5 where they are executed rather than read, and unreferenced files on disk cost nothing in context.

Auto-memory instead of explicit metadata

The post recommends leaning on auto-memory rather than manually maintained context files. The plan metadata header stays manual regardless: it is a durable artifact read by humans and by future agents from the file itself, not a recall aid for one session. Different mechanism, different job.

Risks

  • Description regression. A broader description can over-trigger — firing on any mention of "plan". Scenario A's fresh-session test is the check; if it fires on unrelated prompts, tighten the trigger list rather than the whole description.
  • Placeholder leakage. Once the template is a separate file, a run that skims it instead of reading it fully could ship a {{TOKEN}} into a saved plan. The grep -c '{{' assertion on generated plans is the guard, in both Phase 4 and global validation.
  • Existing specs are markdown. The five plans already in specs/ predate the HTML format. No migration is planned or needed — the skill only reads the plan it is pointed at.

Dependencies

None added. The image scripts already declare their own dependencies inline via uv run script metadata (openai, python-dotenv), and this plan does not touch them. Everything else is markdown, HTML, and shell.
