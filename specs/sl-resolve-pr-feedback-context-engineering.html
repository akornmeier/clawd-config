Purpose

Apply the Claude 5 context-engineering guidance to sl-resolve-pr-feedback, targeting the two things the request names: accuracy — the skill currently ships a path bug that makes every bundled script call resolve to the wrong place, and a tool declaration that contradicts its own workflow — and performance — full-mode.md loads 317 lines on every run, roughly 73 of which cannot apply until after a push that may never happen.

The skill's behaviour is not being redesigned. Its nine-step flow, its verdict taxonomy, its Codex gate and its quiescence gate all survive intact. What changes is what resolves, what loads when, and where each contract is stated exactly once.

Problem

Two of the six findings below are outright defects, not style. The rest are the article's "then vs now" pairs landing on a skill that was written before them: everything upfront, and the same contract restated in three files that must now agree with each other.

Solution

Four phases, ordered by risk. The defects go first because they are live in every run; the context work follows; measurement lands last so it can regress against a known-good baseline rather than a broken one.

  1. Repair the two defects. Re-anchor all ten script invocations on a model-filled SKILL_DIR; correct allowed-tools to match what the workflow actually does.
  2. Split the push-only tail. Move steps 5b and 8 behind a one-line conditional stub each, so a reply-only round never pays for them. codex-gate.md already proves the pattern works.
  3. Collapse the duplicated contracts. Reply templates live only in the agent that writes them; the verdict taxonomy gets one definition and two pointers.
  4. Extend the evals to the core loop. Three scenarios covering triage, verdict selection and the non-actionable silent drop — the paths that decide whether the skill is accurate.

Amendments

2026-07-25 — Three process changes beyond this plan's scope: cluster-before-dispatch, central premise check, re-fetch-before-wait

This plan was scoped to context engineering — where bytes live and when they load. Reviewing the skill's process afterwards surfaced three accuracy problems the plan did not address, and the user asked for all three.

1. Dispatch is now per cluster, not per thread. Reviewers file one thread per location, so one mistake in three files arrives as three threads. Fanning out per thread asked the same question three times in three contexts that could not see each other — they could answer differently on the same PR. Step 3 now groups items sharing a file or a decision; step 4 dispatches one agent per cluster. This subsumes the old file-overlap serialization rule, so two rules became one and all clusters run in parallel.

2. Cited premises are verified once, centrally, before fan-out. Findings that justify themselves with a claim about the repo ("we already use X") are persuasive precisely because of the claim, and the claim is the part most often wrong. An agent handed one thread sees the assertion but not whether it holds repo-wide. Step 3 now checks each distinct claim once and passes the verdict to the cluster that rests on it. This is the step that would have caught the ${CLAUDE_SKILL_DIR} defect without needing a human to think of checking.

3. Step 8 re-fetches before it waits. The old order blocked on bot re-review and only then looked, paying the full timeout even when the reviewer had already responded — and paying it again when the reviewer never would. A re-fetch is one GraphQL call. Now: re-fetch first; new threads mean loop with no wait at all; empty-and-pushed gets a 60s settle window; empty-and-nothing-pushed concludes. The quiescence gate is renamed settle window throughout, and wait-for-bot-review gained an optional fourth argument so the window can be bounded per call (verified: 150s default → 11s with the override).

Not covered by evals. All three are prose behavioural rules — the class this skill's own eval README says nothing but the suite catches. No scenario tests them yet; the existing nine were checked and none regressed.
