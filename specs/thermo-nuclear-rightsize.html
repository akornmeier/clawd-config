Purpose

Cut thermo-nuclear-code-quality-review from 192 lines to roughly 60 by deleting restatements, and resolve a frontmatter contradiction that makes its four advertised trigger phrases unreachable. The skill's opinions are good and stay exactly as they are — this plan removes the four extra times each one is said.

Problem

The skill states seven review rules once, properly, under Non-Negotiable Additional Standards (lines 23–70). It then restates them as questions (Primary Review Questions, 71–88), as flags (What to Flag Aggressively, 89–110), as fixes (Preferred Remedies, 111–134), as quotable phrasings (Review Tone, 135–153), and once more as presumptive blockers (Approval Bar, 183–192). The 1000-line rule appears at lines 34, 36, 95, 144 and 186. All 12.1 KB is forced — there is exactly one bundled file, so every invocation pays for all five voices.

Separately, the frontmatter contradicts itself. The description names four trigger synonyms — "thermo-nuclear code quality review", "thermonuclear review", "deep code quality audit", "especially harsh maintainability review" — while line 4 sets disable-model-invocation: true, which removes the skill from the model's list entirely. Those four phrasings can never match anything. Whichever half is intended, the other is wrong, and a stranger reading the frontmatter is told the opposite of the truth.

Standards 3–7 (lines 46–69) are a third problem of a different kind: "prefer direct, boring, maintainable code over hacky or magical code" and "keep logic in the canonical layer and reuse existing helpers" are general engineering competence, not this team's opinion. They fail the subtraction test. Standards 0, 1 and 2 do not — the 1000-line threshold is a real number and the delete-don't-rearrange bias is a real stance.

Solution

Three deletions and one decision. Non-Negotiable Additional Standards becomes the single owner of the rules; the four restating sections and the Approval Bar's blocker list are deleted outright. Standards 3–7 go with them. Output Expectations stays untouched — its ranked output order is a genuine format contract the model would not invent.

The frontmatter decision is the user's, not the builder's: either delete disable-model-invocation so the advertised phrases work, or keep manual-only invocation and rewrite the description to say so. Phase 1 asks, then implements the answer. Nothing else in the plan depends on which way it goes.

Decisions and rejected alternatives

Split the skill into SKILL.md plus references/

Rejected. Splitting is the fix when a large file contains distinct material that different tasks need. Here the file contains one set of rules said five ways — splitting would give each restatement its own file and preserve the actual defect behind a nicer structure. The grader's phrasing is right: cut rather than split.

Keep Review Tone as a phrase bank in references/

Considered seriously. The quotable phrasings ("this pushes the file past 1k lines. can we decompose this first?") have some value as house voice. Rejected because every phrase encodes a rule already stated in Standards, so the file would reintroduce dimension 5 one hop away. If the voice turns out to matter after Phase 3's live review, add it back deliberately as references/review-phrasing.md read only when drafting final comments — and record that in Amendments.

Decide the frontmatter question in the plan rather than asking

Rejected. Both answers are defensible and they lead to genuinely different skills — one that competes for every diff, and one invoked deliberately when a normal review already passed. That is the user's call about how they want to work, not a defect with a correct fix.

Risk

Over-deletion. The one real risk. Five restatements exist because someone wanted the rules to land, and cutting to a single statement may make the review less insistent even though nothing was removed in substance. Phase 3's live review against a real diff is the only check that can catch it, which is why the plan does not end at wc -l.
